# 文森律所运营工作台 V9.1 后端现状对照与三模块迭代需求

## 1. 文档目的

本文以两份材料为依据：

1. `legal-operations-user-training-guide-v1.md`：从系统后端开发导出的第一版现行业务逻辑，作为“当前系统实际规则”的主要依据。
2. `WENSEN_AI_V9.1_业务变更与项目重开功能设计.md`：作为 V9.1 后续产品迭代的目标方案。

本文按以下三个模块整理：

- 工时管理。
- 项目管理。
- 合同管理。

每个模块分别说明：

- 后端现有能力和业务规则。
- V9.1 已有或已通过小版本补充的能力。
- 当前规则与目标方案之间的差异。
- 建议新增或调整的迭代需求。
- 需要落到后端的状态、数据、权限和联动逻辑。

本文只梳理产品与业务需求，不涉及代码实现。

## 2. 总体结论

当前后端已经具备客户、项目、合同、工时、日报审批、应收、开票、回款和核销的基础闭环，但整体模型偏向“一次创建、一次审批、结束后只读”。本次迭代的核心，是在不破坏历史财务事实的前提下，增加以下能力：

1. 工时从“本人登记＋日报审批”升级为“本人登记或代填＋统一工时状态＋审批后更正”。
2. 项目从归档后永久只读，升级为支持受控重新打开。
3. 项目重开时可以调整当前负责人、成员和所属部门，但不覆盖归档前的历史归属。
4. 合同从“审批通过后不可变”升级为支持审批中撤回重传、已审批后文件更正、内容变更、作废和终止。
5. 客户、项目、合同、应收、发票、回款和核销使用版本、快照和变更记录连接，不能通过直接修改上游对象覆盖历史数据。

三个模块需要共用一套“业务变更申请”能力：

```text
原业务记录
  → 发起变更
  → 保存原始快照
  → 填写变更内容、原因和生效日期
  → 系统计算影响范围
  → 审批
  → 通过后生成新版本或项目重开记录
  → 原记录保留为历史
```

## 3. 需要先统一的产品口径

## 3.1 合同是否存在草稿状态

当前已确认的 V9.1 产品口径是“只有合同上传，不设置独立草稿状态”。

本方案采用以下目标口径：

- 不新增合同草稿箱。
- 合同上传并提交后进入“审批中”。
- 审批中可以撤回删除或重新上传。
- 审批退回后进入“待修改”，修改后重新提交。

研发实施前需要核对后端接口是否实际存在未提交合同记录：

- 如果后端没有草稿，仅修正文档和状态枚举。
- 如果后端存在技术性临时记录，则只作为未完成上传的系统暂存，不在用户端展示为正式合同状态。

## 3.2 项目负责人和服务负责人

当前后端规则：

- 项目创建人自动成为项目负责人。
- 项目负责人不能在创建时另选。
- 服务负责人是另一个字段，不替代项目负责人。

目标方案需要允许项目重开时调整当前项目负责人，但不能覆盖归档前负责人。项目仍保留一个当前负责人，同时在重开记录和审计日志中保存归档前负责人快照，不额外建设前台“服务周期”模块。

## 3.3 工时正式口径

当前后端正式工时报表只统计直属上级已经批准的日报工时。V9.1.1 将代填确认和日报审批统一到一个“工时状态”字段，不再分别设置本人确认状态和日报审批状态。

目标口径为：

```text
工时记录人＝承办律师
  → 未提交 → 审批中 → 已通过/已退回/已撤回

工时记录人≠承办律师
  → 待确认 → 已通过/已退回

已通过工时被正式业务使用
  → 已锁定
```

工时状态为“已通过”或“已锁定”时进入正式统计。

## 4. 工时管理模块

## 4.1 后端现有能力提取

### 4.1.1 入口和权限

- 工作台“工时记录”。
- 计时管理“新增计时”。
- 项目详情“计时—新增计时”。
- 普通员工只能登记本人计时。
- 项目成员可以登记本人项目计时。
- 当前后端没有为其他人员代填工时的正式业务流程。

### 4.1.2 工时类型

| 工时类型 | 客户/项目要求 | 计费工时 |
| --- | --- | --- |
| 律所运营类工作 | 不关联客户和项目 | 不填写 |
| 常法合同计时 | 必须关联客户和项目 | 可以填写 |
| 非常法项目工作 | 必须关联客户和项目 | 不填写 |

### 4.1.3 字段和校验

- 工作日期不得晚于当天。
- 客户和关联项目。
- 客户对接人。
- 工作类型。
- 工作方式。
- 工作内容。
- 实际用时。
- 完成状态。
- 实际用时按 0.1 小时记录。
- 单条实际用时为 0.1～24 小时。
- 同一员工同一天累计不得超过 24 小时。
- 常法计费工时不得超过实际用时。
- 项目工时最多上传 10 个附件，单个不超过 20 MB。
- 项目工时附件同步进入项目文件与成果及知识中心。
- 律所运营类工作不能上传项目附件。

### 4.1.4 修改和删除

- 尚未纳入日报的工时可以修改或删除。
- 纳入日报后不能删除。
- 纳入日报后，核心业务字段锁定。
- 纳入日报后只能更新完成状态、完成日期和备注。

### 4.1.5 今日日报

- 日报汇总当前用户当天全部有效计时。
- 日报同时纳入完成状态为“进行中”和“已完成”的有效工时；完成状态表示工作事项进度，不作为能否提交日报的判断条件。
- 日报按工时记录的“工作日期”归集，不按记录创建时间或工作完成日期归集。
- 系统每天 23:00 自动提交当天符合条件且尚未提交的日报，作为用户忘记手工提交的兜底。
- 当天无计时不能提交。
- 同一天已经提交或批准后不能重复提交。
- 日报包含暂停或不可写项目时不能提交。
- 日报必须存在有效直属上级，不支持无上级自动通过。
- 系统不向普通用户提供通用的历史日报补交入口。
- 未纳入日报的工时不进入正式报表。

### 4.1.6 报表

当前正式报表只统计直属上级已批准的日报工时：

- 管理统计。
- 客户工时表。
- 按人员统计实际工时、计费工时、项目数和记录数。
- 待审批或被拒绝的日报不进入正式报表。

三个工时报表页签已经通过小版本迭代完成，本次不重复建设页面结构，只调整状态和取数规则。

## 4.2 V9.1 已补充能力

- 统一工时台账。
- 受控代为填报。
- 分别记录工时记录人和承办律师。
- 代填原因必填。
- 仅当工时记录人与承办律师不同时，工时进入“待确认”。
- 承办律师可确认或退回。
- 待确认代填工时不进入正式统计。
- “记录我的相关工时”可复用公共工作信息创建本人记录。
- 待确认和异常记录集中展示。

## 4.3 现状与目标差异

| 差异 | 当前后端 | 目标要求 |
| --- | --- | --- |
| 代填工时 | 只能登记本人 | 授权角色可代填，承办律师确认 |
| 代填确认与日报 | 无代填确认层 | 使用统一工时状态承接承办律师确认和日报审批 |
| 已审批工时修改 | 核心字段锁定，无更正流程 | 发起更正审批，生成新版本 |
| 已审批工时删除 | 不允许删除 | 发起撤回审批，保留原记录 |
| 当日漏交 | 23:00 自动提交兜底 | 明确自动提交范围、失败重试和管理员重跑机制 |
| 承办律师调整 | 不支持 | 特殊变更流程，不作为普通编辑 |
| 锁定期 | 只有“纳入日报”锁定 | 增加客户报表、计费、绩效等锁定层级 |
| 项目重开 | 无重开能力 | 重开后新增工时继续关联原项目，并通过重开记录保留时间边界 |

## 4.4 工时迭代需求

### TIME-01：统一工时状态模型

优先级：P0。

不再分别设置“登记来源”“本人确认状态”“日报审批状态”和“记录有效性”。工时记录只保留一个统一的“工时状态”字段。

工时状态枚举值：

- 未提交。
- 审批中。
- 待确认。
- 已通过。
- 已退回。
- 已撤回。
- 已锁定。

系统继续保存“工时记录人”和“承办律师”两个事实字段，但不再保存独立的登记来源状态：

| 场景 | 状态流转 |
| --- | --- |
| 工时记录人＝承办律师 | 保存后为“未提交”；提交日报后为“审批中”；审批通过后为“已通过”；驳回后为“已退回”；主动撤回后为“已撤回” |
| 工时记录人≠承办律师 | 保存后为“待确认”；承办律师确认后为“已通过”；承办律师退回后为“已退回” |
| 已通过工时进入正式报表、计费、绩效或薪酬结算 | 状态更新为“已锁定” |

其中，“已通过”表示该条工时已经完成其所需的确认或审批，可以进入正式统计；“已锁定”表示该条工时已经被后续正式业务使用，不能直接修改。

正式报表取数条件：

```text
工时状态为“已通过”或“已锁定”
```

### TIME-02：代填权限和范围

优先级：P0。

| 角色 | 代填范围 |
| --- | --- |
| 项目负责人 | 所负责项目的项目成员 |
| 团队负责人 | 本团队成员 |
| 办公室管理员 | 本办公室人员 |
| 系统管理员 | 授权范围内特殊补录 |

普通员工不能为他人代填。

### TIME-03：代填确认闭环

优先级：P0。

- 仅当工时记录人与承办律师不同时，保存后状态为“待确认”并通知承办律师。
- 承办律师确认或退回。
- 退回原因必填。
- 承办律师确认后，工时状态更新为“已通过”。
- 承办律师退回后，工时状态更新为“已退回”。
- 工时记录人可以撤回待确认记录，状态更新为“已撤回”；修改后再次提交时重新进入“待确认”。
- 状态为“已通过”或“已锁定”后，工时记录人不能直接修改。

### TIME-04：代填工时与日报整合

优先级：P0。

- 工时记录人等于承办律师时，工时通过日报完成审批，状态依次为“未提交—审批中—已通过/已退回/已撤回”。
- 工时记录人不等于承办律师时，由承办律师直接确认；确认后状态为“已通过”，不再设置独立的“本人确认状态”。
- 状态为“待确认”“已退回”或“已撤回”的工时不进入正式统计。
- 当天仍有“待确认”的代填记录时不纳入日报，也不阻断其他“未提交”工时提交。
- 日报详情展示工时记录人和承办律师。

### TIME-05：审批中撤回及驳回后重新提交

优先级：P1。

- 日报尚未完成审批时允许申请人撤回，所含工时状态更新为“已撤回”。
- 撤回后关闭原审批任务；再次编辑时工时状态恢复为“未提交”。
- 修改工时后重新提交日报，工时状态更新为“审批中”并生成新审批编号。
- 原审批节点保留历史记录。
- 日报被驳回后，其中的工时状态更新为“已退回”，工时记录恢复为可修改，并向填报人展示驳回原因。
- 填报人修改或删除被指出的工时后，从原工作日期的日报详情点击“重新提交”。
- 重新提交沿用原日报业务编号和工作日期，生成新的日报版本及审批编号；原提交内容、驳回意见和审批过程保留为历史。
- 代填工时被承办律师退回后，由工时记录人修改并重新提交确认，状态重新进入“待确认”。

### TIME-06：已审批工时更正

优先级：P1。

- 操作名称为“申请更正”，不使用普通编辑。
- 展示原值和新值。
- 更正原因必填。
- 原审批人或项目负责人审批。
- 审批期间报表继续使用原版本。
- 更正申请作为独立审批对象记录审批进度，不增加新的工时状态。
- 审批期间原工时继续保持“已通过”或“已锁定”，报表继续使用原版本。
- 通过后新版本生效；原版本进入版本历史，不再使用“已被更正”作为工时状态。

### TIME-07：已审批工时撤回

优先级：P1。

- 已审批记录不能物理删除。
- 需要取消已审批工时时发起撤回申请，申请本身使用独立审批记录，不增加“作废中”状态。
- 审批通过后工时状态更新为“已撤回”，并退出工时报表、客户报表和绩效统计。
- 原记录和审批历史继续可查。

### TIME-08：承办律师变更

优先级：P2。

- 仅项目负责人、工时管理员或系统管理员可发起。
- 记录原、新承办律师及转移原因。
- 通知双方。
- 审批通过后变更当前归属，原工时记录人不变。

### TIME-09：自动提交兜底

优先级：P2。

- 每天 23:00 的自动提交任务按员工和工作日期汇总当日符合条件的有效工时。
- 自动提交只处理状态为“未提交”的工时，包括完成状态为“进行中”和“已完成”的记录；“待确认”“已退回”“已撤回”和“已锁定”不重复提交。
- 自动任务必须幂等：同一员工、同一日期已经存在日报时不得重复创建。
- 自动提交失败时由系统重试并产生运维告警，授权管理员可以重跑该日期的自动提交任务。
- 如果当日 23:00 时没有工时，后续确需补录时填写补录原因和实际工作日期；系统根据工时记录人与承办律师是否相同，分别进入“未提交”或“待确认”。

### TIME-10：项目重开后的工时边界

优先级：P1。

- 项目重开前的历史工时保持只读。
- 项目重开后的新增工时继续关联原项目，不新增用户可见的“服务周期”字段。
- 后端可通过工时创建时间和对应的项目重开申请编号识别其属于重开后新增数据。
- 项目归档、终止或重开审批中不允许新增工时。

### TIME-11：锁定期间

优先级：P2。

当“已通过”工时被用于客户正式报表、计费、开票依据、绩效或薪酬结算时，工时状态更新为“已锁定”。已锁定工时只能走特殊更正，由对应管理角色审批；更正审批期间仍保持“已锁定”。

## 4.5 工时底层逻辑

1. 工时更正生成新版本，不覆盖原记录。
2. 工时记录保存工时记录人、承办律师和实际确认人；不再保存独立的登记来源状态。
3. 承办律师确认和日报审批共用一个“工时状态”字段，系统根据工时记录人与承办律师是否相同决定进入“待确认”还是“未提交”。
4. 日报保存提交时的工时版本集合，避免后续修改改变原审批内容。
5. 更正通过后，系统更新正式报表使用的当前版本，但保留原日报审批快照和历史版本。
6. 已审批工时撤回后状态为“已撤回”，不删除附件、审批和审计记录。
7. 同一天 24 小时校验按承办律师计算，而不是按工时记录人计算。
8. 计费工时限制继续沿用现有计费类型规则。

## 5. 项目管理模块

## 5.1 后端现有能力提取

### 5.1.1 立项字段

- 正式客户。
- 项目名称。
- 项目类型：常年法律服务、专项非诉、诉讼仲裁。
- 立项时间。
- 服务主体。
- 服务负责人。
- 项目成员。
- 服务内容。
- 目标结束日期和备注可选。

### 5.1.2 项目负责人规则

- 项目创建人自动成为项目负责人。
- 创建时不能另选项目负责人。
- 创建人自动成为项目成员。
- 项目负责人不能被移出。
- 服务负责人表示服务责任，不替代项目负责人。

### 5.1.3 立项审批

- 创建项目后读取创建人的 HR 任职和直属上级。
- 项目进入“项目审批中”。
- 直属上级审批通过后进入“进行中”。
- HR 明确无直属上级时可以按规则自动通过。
- 任职或上级数据未同步时返回错误，不自动通过。
- 被拒绝后由创建人修正并重新提交。

### 5.1.4 项目权限

- 项目成员可维护合同、风险、文件、本人计时、结算期次和开票申请。
- 只有项目创建人可编辑基本资料、维护成员和发起生命周期审批。
- 非项目成员只读。
- 项目负责人不能被移出。
- 历史成员记录不物理删除。

### 5.1.5 生命周期

| 操作 | 当前规则 |
| --- | --- |
| 项目变更 | 项目负责人填写原因并按规则审批 |
| 延期 | 填写新结束日期和原因，直属上级审批 |
| 暂停 | 填写原因，直属上级审批 |
| 恢复暂停 | 直接恢复，不发审批，保留审计 |
| 终止 | 填写原因，直属上级审批 |
| 结项 | 所有有效结算期次全部核销后才能发起，直属上级审批 |
| 归档 | 结项通过后进入已归档 |

“结项”和“归档”不是两个并列的最终状态：结项是申请及审批动作，“待结项”和“结项审批中”是过程状态；结项审批通过后，项目直接进入最终状态“已归档”，不再保留独立的长期“已结项”状态。

### 5.1.6 暂停后的限制

- 项目资料、成员、合同、计时、应收、开票、文件和风险均不可新增或修改。
- 在途合同、开票和日报审批不能继续处理。
- 只允许对暂停前已开具且尚未全部核销的发票登记回款。
- 恢复后其他业务能力重新开放。

## 5.2 现状与目标差异

| 差异 | 当前后端 | 目标要求 |
| --- | --- | --- |
| 项目重开 | 已归档只读，无重开 | 已归档可申请重新打开 |
| 重开历史 | 无 | 增加后台重开记录，保留归档前后边界 |
| 项目负责人 | 永久固定为创建人 | 重开时可调整当前负责人，保留归档前负责人快照 |
| 项目成员 | 当前名单＋历史删除记录 | 重开时可调整当前成员，保留历史成员记录 |
| 所属部门 | 主要依赖服务主体 | 明确项目所属部门及自动带出的部门负责人 |
| 已终止恢复 | 无 | 误终止可撤销，真实终止后重新合作应新建项目 |
| 归档条件 | 所有有效期次必须核销 | 保持现有强规则，不允许带未结财务归档 |
| 归档后财务 | 文档未完整说明 | 归档前财务记录全部只读，重开不得修改 |

## 5.3 项目迭代需求

### PROJECT-01：项目重开记录

优先级：P0。

不增加独立、复杂的“项目服务周期”业务模块。项目仍使用现有开始日期、目标结束日期和项目状态；后台通过归档记录和重开记录保存各次执行边界，产品端只在现有“项目概览”中展示当前项目服务周期。

重开记录包括：

- 项目 ID。
- 重开申请编号。
- 阶段序号。
- 归档时间。
- 归档前项目开始日期和结束日期快照。
- 重新打开日期。
- 重开原因和新增工作范围。
- 重开前、后的负责人、成员和所属部门快照。
- 新目标结束日期。
- 合同处理结论。
- 审批人及审批时间。

项目开始日期保持原立项日期，不因重开而修改；当前目标结束日期可以在重开审批通过后更新，原结束日期保存在归档和重开记录中。

阶段编号规则：

- 项目首次立项审批通过后为“第一期”。
- 已归档项目正常重开审批通过后，阶段序号加一，例如第二期、第三期。
- 重开申请被撤回、退回或拒绝时，不增加阶段序号。
- 项目延期、暂停和恢复属于当前阶段内的状态变化，不增加阶段序号。
- 误归档撤销属于纠错，恢复原阶段，不增加阶段序号。
- 每一期从立项通过或重开生效开始，到该次结项审批通过并再次归档时结束。
- 所有有效结算期次完成核销并通过结项审批后，该期标记为“已完整归档”。
- 如果项目终止，该期标记为“已终止”，不视为完整归档，也不能通过普通重开进入下一期。

产品端展示：

- 在现有“项目概览”的基本信息中增加“项目服务周期”，展示“第一期 · 进行中”“第一期 · 已归档”或“第二期 · 进行中”。
- 不新增“项目历程”区域，也不重复展示合同、审批和财务数据。
- 归档和重新打开事件继续显示在现有“项目动态”和“审批记录”中。
- 在现有“项目成员”区域增加“当前成员/历史成员”切换；历史成员显示所属期次、加入时间、退出时间和当时角色，全部只读。

### PROJECT-02：已归档项目重新打开

优先级：P0。

新增“申请重新打开”，填写：

- 重开类型和原因。
- 新服务范围。
- 重开日期和新预计结束日期。
- 当前项目负责人、服务负责人和成员。
- 项目所属部门或团队。
- 是否继续使用原合同。
- 是否需要补充协议或新合同。
- 当前风险和重开后预算工时。

功能入口：

- 项目台账中，已归档项目的操作列显示“申请重新打开”。
- 已归档项目详情页右上角显示“申请重新打开”。
- 其他项目状态不显示该入口。

审批通过后新增项目重开记录：原合同仍有效时项目进入“进行中”；原合同到期、终止、作废或需要补充协议时统一进入“待合同”。是否需要补充协议作为合同处理类型展示，不新增“待补充协议”项目状态。

### PROJECT-03：撤销误归档

优先级：P1。

“误归档”不能由系统仅根据时间自动判断，由申请人选择“撤销误归档”，系统校验适用条件，再由原结项审批人判断并审批。

适用条件：

- 原归档决定本身存在误操作或事实判断错误，项目在归档时实际并未完成。
- 没有新的客户指令、新增服务范围、新收费安排或新合同需求。
- 不需要重新设定一个新的业务执行阶段。
- 归档后没有产生新的外部业务事实。
- 归档结果尚未进入已经关闭的经营统计期间；已经进入锁定统计期间时使用普通重新打开，不回改历史归档口径。
- 原项目负责人申请撤销，并填写具体误归档原因和证明。

不适用情形：

- 项目原来已经正常完成，后来客户新增工作。
- 需要新增或变更合同、费用和服务范围。
- 归档后间隔一段时间重新开始合作。

审批通过后：

- 原归档记录标记为“已撤销”，但不删除。
- 项目恢复归档前状态。
- 项目服务周期序号不增加，仍属于原一期。
- 原负责人、成员、合同和财务历史不变。

不满足误归档条件时，必须使用普通“申请重新打开”，审批通过后进入下一期。

### PROJECT-04：项目重开字段控制

优先级：P0。

允许编辑重开后生效的当前字段：

- 新服务范围和日期。
- 当前负责人、服务负责人和成员。
- 所属部门或团队。
- 合同使用方案。
- 重开后预算和风险。

不允许修改历史事实：

- 项目编号。
- 原创建时间和立项审批。
- 原项目开始日期、归档时间和归档记录。
- 原归档或终止原因。
- 原负责人和成员快照。
- 历史合同、工时和财务记录。

### PROJECT-05：项目负责人调整

优先级：P1。

- 创建人继续保留为归档前负责人记录。
- 重开时允许选择当前项目负责人。
- 新负责人必须是有效员工，并满足项目服务主体或组织范围规则。
- 负责人变化从项目重开生效时间起生效。
- 原负责人的历史业绩和审批记录不重新分配。

### PROJECT-06：项目所属部门及部门负责人

优先级：P1。

- 项目增加明确的所属部门或团队。
- 所属部门负责人从 HR 组织架构自动带出，不在项目中手工选择。
- 变更所属部门时，原部门负责人确认移出，新部门负责人确认接收。
- 跨办公室时增加办公室负责人审批。
- 历史工时和业绩保持原部门快照，重开后的新增业务按新部门统计。

### PROJECT-07：项目成员重开调整

优先级：P1。

- 重开时可保留、移除或新增成员。
- 移除成员不删除历史参与记录。
- 当前负责人必须属于当前项目成员。
- 成员权限从重开生效日期起按新的成员名单判断。

### 5.3.7 本期不覆盖的客户主体能力

以下能力暂不纳入本期项目重开范围，继续沿用当前“项目固定关联一个主客户”的后端规则：

- 一个项目关联多个客户主体。
- 同一客户名称变更。
- 增加或替换项目主客户。
- 客户主体承继及应收转移。

项目重开时客户主体保持原值且不可编辑。上述能力后续单独立项，不与本期项目重开同时上线。

### PROJECT-08：误终止撤销

优先级：P1。

- 仅用于误操作终止。
- 填写原因并由原终止审批人审批。
- 通过后恢复终止前状态。
- 保留终止和撤销终止历史。

### PROJECT-09：真实终止后重新合作

优先级：P1。

- 原项目继续保持已终止。
- 从原项目创建关联的新项目。
- 复用客户和基础资料，但重新完成准入、利冲、立项和合同流程。
- 新旧项目在详情中互相关联。

### PROJECT-10：归档和终止前置检查

优先级：P1。

归档或终止前检查：

- 审批中合同。
- 待确认和审批中工时。
- 未完成合同变更。
- 未开票、逾期、已开票未回款和待核销事项；存在任一有效未核销期次时不得申请归档。
- 文件交接和风险事项。

归档继续坚持现有强规则：

- 所有有效结算期次必须全部完成核销，才能申请结项和归档。
- 不提供带未结应收归档的特别审批。
- 结项是申请和审批过程，不单独形成长期“已结项”状态；结项审批通过后项目直接进入“已归档”。

### PROJECT-11：项目状态与业务权限

优先级：P0。

| 项目状态 | 新增工时 | 合同操作 | 新增应收/开票 | 历史回款/核销 |
| --- | --- | --- | --- | --- |
| 进行中 | 允许 | 允许 | 允许 | 允许 |
| 待合同 | 仅允许非计费或受限工作 | 可上传合同 | 不允许 | 允许 |
| 暂停 | 不允许 | 只读或受控变更 | 不允许 | 允许 |
| 已归档 | 不允许 | 只读 | 不允许 | 只读 |
| 已终止 | 不允许 | 只读 | 不允许 | 允许 |
| 重开申请中 | 不允许 | 只读 | 不允许 | 只读 |

## 5.4 项目底层逻辑

1. 项目主表继续保存当前状态、项目开始日期和当前目标结束日期，不增加独立的服务周期业务模块。
2. 重开时新增后台重开记录，保存归档前日期、负责人、成员、部门及审批快照。
3. 所属部门负责人从 HR 组织关系动态解析，同时在审批提交时保存审批人快照。
4. 重开不复制原合同、工时、应收、发票、回款和核销。
5. 已归档项目的原财务信息永久只读；重开后不得修改原应收、发票、回款和核销。
6. 重开后如需新增收费业务，只能基于继续有效的合同、新合同或批准的合同变更产生新应收。
7. 项目重开后的新增业务通过创建时间和来源重开申请编号与历史数据区分；产品端仅在“项目概览”的“项目服务周期”字段展示“第一期、第二期”。
8. 已终止项目和已归档项目使用不同恢复规则。

## 6. 合同管理模块

## 6.1 后端现有能力提取

### 6.1.1 使用前提和权限

- 项目已完成立项审批并处于可履约状态。
- 当前用户是项目有效成员。
- 项目负责人的 HR 任职和直属上级有效。
- 项目成员可以新增合同。

### 6.1.2 合同字段

- 合同名称。
- 服务类型。
- 签约日期和可选到期日期。
- 服务内容简介和备注。
- 合同源文件可选，也可以完全手填。
- 客户签约主体固定继承项目主客户，不允许在合同中更换。
- 我方签约主体及比例。
- 案件来源人或团队及案源提成。
- 服务团队、负责人和分配比例。
- 币种、计费方式、付款方式和分期方式。
- 结算明细。

### 6.1.3 计费与结算

支持：

- 小时计费，无封顶价。
- 小时计费，有封顶价。
- 固定总价。
- 固定基础费用加风险费用。

除无封顶小时计费外，结算明细税前总额必须等于合同计费金额。无封顶小时计费审批通过时不生成期次，可由项目成员在实际账单确认后手工添加。

### 6.1.4 合同审批

- 审批人取项目负责人的直属上级，而不是合同录入人的直属上级。
- 有有效上级时进入“审批中”。
- HR 明确无直属上级时可按规则自动通过。
- 任职、上级快照或账号缺失时不能保存为已通过。
- 退回后进入“待修改”，项目成员可修改并重新提交。
- 审批通过后变为“已批准”，并按付款计划生成结算期次。

### 6.1.5 当前缺失

- 审批中合同撤回删除。
- 审批中合同重新上传。
- 已审批合同文件更正。
- 已审批合同内容变更。
- 合同作废和合同终止。
- 合同版本及生效日期。
- 项目重开后的合同复用或补充协议机制。

## 6.2 现状与目标差异

| 差异 | 当前后端 | 目标要求 |
| --- | --- | --- |
| 审批中删除 | 无 | 撤回审批并逻辑删除 |
| 审批中重传 | 无 | 保留编号，替换文件后重新审批 |
| 补充材料 | 退回后修改 | 不改正文时可补充材料，不重启审批 |
| 已审批文件错误 | 无更正机制 | 文件更正审批，保留原文件 |
| 已审批内容变化 | 不支持 | 生成新合同版本和变更审批 |
| 作废 | 不支持 | 无下游财务时可申请作废 |
| 终止 | 无独立合同终止 | 提前结束履行并处理未来期次 |
| 项目重开 | 无 | 判断原合同有效性、范围和剩余额度 |
| 财务联动 | 审批通过一次性生成期次 | 只调整未来未使用期次，历史财务锁定 |

## 6.3 合同迭代需求

### CONTRACT-01：合同状态统一

优先级：P0。

目标状态：

- 审批中。
- 待修改。
- 已拒绝。
- 已批准。
- 变更审批中。
- 已作废。
- 已终止。

不在用户产品中增加独立草稿状态。

### CONTRACT-02：审批中撤回并删除

优先级：P0。

- 上传人或项目负责人可操作。
- 原审批标记申请人撤回。
- 合同退出普通台账。
- 后端保留合同编号、文件、审批及删除日志。
- 如果已经产生任何结算期次或其他下游数据，不允许走此操作。

### CONTRACT-03：审批中重新上传

优先级：P0。

- 保持合同编号。
- 原文件标记“已替换”。
- 原审批流程关闭。
- 填写重新上传原因。
- 新文件重新提交审批并生成新审批编号。
- 审批人可以对比新旧文件。

### CONTRACT-04：审批中补充材料

优先级：P1。

- 不替换合同正文。
- 不重启审批。
- 记录补充人、时间和附件分类。
- 通知当前审批人。

### CONTRACT-05：已审批合同文件更正

优先级：P1。

适用于错传、漏页或扫描不清，且合同内容没有变化：

- 上传正确文件。
- 更正原因必填。
- 原合同审批人确认。
- 新文件成为当前展示版本。
- 原文件保留为历史。
- 合同金额和结算期次不变。

### CONTRACT-06：已审批合同内容变更

优先级：P0。

适用于主体、范围、期限、金额、税率、付款方式、收款账户、结算计划或团队分配变化：

- 创建合同新版本。
- 保存原值和新值。
- 上传补充协议或其他变更依据。
- 原版本在审批期间继续有效。
- 审批通过后按生效日期切换当前有效版本。

### CONTRACT-07：合同作废

优先级：P1。

- 无结算期次、开票、回款和核销时可以申请作废。
- 只有未使用结算期次时，可在作废审批通过后同步取消。
- 已产生开票、回款或核销时不允许作废。
- 作废后合同编号和记录继续保留。

### CONTRACT-08：合同终止

优先级：P1。

- 记录终止原因和生效日期。
- 处理未来未开票结算期次。
- 保留已发生应收、开票、回款和核销。
- 提示是否同步暂停或终止项目，但不能自动改变项目状态。

### CONTRACT-09：合同与项目重开

优先级：P0。

- 原合同仍有效且覆盖新工作时，重开项目继续使用原合同。
- 不复制合同和结算期次。
- 原合同到期、终止、作废或范围不覆盖时，项目统一进入“待合同”。
- 如果只需要补充协议，在合同处理信息中标记“需补充协议”，不增加项目状态。
- 新合同或合同变更可记录来源重开申请编号，用于后台审计；项目端通过阶段序号展示所属项目历程，不新增独立服务周期关联页面。

### CONTRACT-10：合同额度延续

优先级：P0。

- 有封顶小时合同重开后继续使用原剩余额度。
- 不因项目重开重置封顶价或已使用金额。
- 无封顶小时合同按实际账单或批准期次累计。
- 固定基础费用与预计风险费用分开计算。

### 6.3.11 本期不覆盖的合同客户主体能力

以下能力暂不纳入本期：

- 多个客户签约主体。
- 同一客户更名后的合同展示和处理。
- 合同主体承继。
- 因主体承继产生的应收转移。

本期合同客户签约主体继续固定继承项目主客户。

### CONTRACT-11：结算期次调整

优先级：P0。

- 未开票、未回款的未来期次可以调整或取消。
- 开票审批中的期次必须先处理审批。
- 已开票、已回款、已核销期次不可覆盖。
- 调减后的合同金额不得低于已开票金额或已确认收入。
- 调增只生成增量期次，不复制原期次。

## 6.4 合同底层逻辑

1. 合同主记录保存合同身份，合同版本保存正文和商业条款。
2. 同一时间只有一个当前有效合同版本。
3. 合同审批通过时生成版本对应的结算计划和应收期次。
4. 后续变更只对未来未使用期次产生增量、替换或取消记录。
5. 已发生的开票、回款和核销始终关联发生时的合同版本与期次快照。
6. 文件更正和内容变更使用不同流程；文件更正不得改变结构化合同字段。
7. 合同作废与合同终止使用不同语义：作废表示登记不应有效，终止表示合同曾有效但提前结束。
8. 本期合同客户主体继续继承项目主客户，不增加多主体和主体承继逻辑。

## 7. 三模块与财务的联动

## 7.1 项目重开不直接改变财务数据

项目重开只恢复项目的后续业务能力，不执行以下操作：

- 不复制合同。
- 不复制结算期次。
- 不重新生成应收。
- 不重置逾期日期。
- 不修改历史发票。
- 不修改历史回款和核销。

## 7.2 合同决定新增收费依据

项目重开后：

| 合同状态 | 项目业务结果 |
| --- | --- |
| 原合同有效且覆盖范围 | 正常进行，可继续登记计费工时和使用剩余期次 |
| 原合同有效但范围不覆盖 | 项目进入待合同，合同处理原因为“需补充协议” |
| 原合同到期 | 待合同 |
| 原合同终止或作废 | 必须新合同 |
| 合同审批中 | 待合同审批 |
| 合同变更审批中 | 原版本继续处理原业务，新业务受限 |

## 7.3 应收规则

- 项目重开本身不生成应收。
- 新应收只能来自有效合同、补充协议、新合同或授权的手工期次。
- 项目能够归档的前提是所有有效期次已经完成核销，因此归档前财务记录在重开后全部保持只读。
- 已取消期次不因重开自动恢复。
- 新应收必须来自重开后继续有效的合同、新合同或批准的合同变更，并记录来源重开申请编号和合同版本。

## 7.4 开票规则

新开票选择链路：

```text
项目
  → 合同及版本
  → 应收期次
  → 开票申请
```

- 一次申请继续遵守同币种、同合同或全部无合同期次的现有规则。
- 项目处于待合同或重开审批中时不能新增正式开票申请。
- 历史发票保留原购方、税号、金额和合同版本。

## 7.5 回款和核销规则

- 暂停和已终止项目仍可按现有规则处理终止前的历史回款和核销。
- 已归档项目因归档前已经完成全部有效期次核销，原财务信息全部只读，不再新增、修改、冲正或重新分配。
- 重开审批中，归档前财务信息继续只读。
- 回款记录实际付款方，不强制等于当前主客户。
- 一笔回款继续支持核销同一项目多张发票。
- 项目重开后新增的合同、应收、发票和回款记录来源重开申请编号，用于与归档前只读数据区分。
- 错误回款继续通过整笔冲正处理。
- 项目重开不自动重分配归档前核销。

## 8. 公共审批、权限和审计需求

## 8.1 统一业务变更申请

支持以下申请类型：

- 工时更正、撤回和承办律师变更。
- 项目重开、撤销误终止、负责人变更和所属部门变更。
- 合同重传、文件更正、内容变更、作废和终止。

申请统一记录：

- 业务对象和原记录编号。
- 原始版本。
- 申请类型和原因。
- 修改前和修改后内容。
- 生效日期。
- 影响分析。
- 附件。
- 申请人、审批人和处理时间。

## 8.2 影响分析

提交前自动检查：

- 是否影响正式工时或已提交日报。
- 是否存在审批中合同。
- 是否影响合同金额或结算期次。
- 是否存在开票审批占用金额。
- 是否存在已开票、已回款或已核销数据。
- 是否需要财务审批。
- 是否需要新合同或补充协议。

## 8.3 并发和版本控制

继续沿用当前后端的数据冲突校验，并扩展到所有变更操作：

- 提交变更时校验原记录版本号。
- 原记录已被其他用户更新时返回冲突。
- 用户刷新后重新查看最新数据及影响分析。
- 不允许重复提交同一变更。

## 8.4 审计日志

审计记录至少包括：

- 操作人和角色。
- 操作时间。
- 变更类型。
- 原值和新值。
- 撤回、退回、批准、拒绝和生效过程。
- 文件版本变化。
- 自动检查结果。
- 关联工时、项目、合同及财务对象。

## 9. 建议实施顺序

## 9.1 第一阶段：状态和版本基础

1. 统一工时状态，打通代填确认和日报审批。
2. 建立统一业务变更申请、原值/新值对比和审计日志。
3. 建立项目归档和重开记录，并在项目详情以第一期、第二期轻量展示项目历程。
4. 建立合同版本。
5. 增加业务对象版本号和并发校验。

## 9.2 第二阶段：核心业务闭环

1. 已审批工时更正和撤回。
2. 审批中合同撤回删除、重新上传和补充材料。
3. 已审批合同文件更正和内容变更。
4. 已归档项目重新打开。
5. 项目负责人、成员和所属部门从重开生效时间起调整，并保留归档前快照。

## 9.3 第三阶段：合同与财务联动

1. 合同金额及未来结算期次调整。
2. 项目重开后新合同、新应收、开票和回款记录来源重开申请编号。
3. 归档前财务信息只读控制。
4. 项目重开后新增财务数据与历史财务数据分区展示。

## 9.4 第四阶段：复杂纠错和治理

1. 锁定期间工时特殊更正。
2. 23:00 自动提交失败重试及管理员重跑。
3. 发票红冲和作废。
4. 跨办公室所属部门变更。
5. 统一异常与变更管理中心。

## 10. 核心验收标准

### 10.1 工时

1. 工时记录人与承办律师不同时，工时必须由承办律师确认后才能变为“已通过”。
2. 只使用一个工时状态字段，状态枚举严格限定为“未提交、审批中、待确认、已通过、已退回、已撤回、已锁定”。
3. 已审批工时只能通过更正或撤回申请调整。
4. 更正审批期间正式报表继续使用原版本。
5. 项目重开后的工时继续关联原项目，并记录来源重开申请；历史工时不变。

### 10.2 项目

1. 已归档项目可发起重开审批。
2. 重开通过后生成后台重开记录，并在项目历程中生成下一期；不新增独立服务周期模块。
3. 重开时可调整当前负责人、成员和所属部门，归档前快照不重算。
4. 误终止和真实终止后的重新合作使用不同流程。
5. 项目重开不自动生成合同、应收、发票或回款。
6. 所有有效结算期次未全部核销时不能申请结项和归档。
7. 项目归档前财务信息在重开后保持只读。

### 10.3 合同

1. 审批中合同可以撤回删除或重新上传。
2. 已审批合同不能直接覆盖或物理删除。
3. 文件更正不改变结构化合同条款和财务数据。
4. 合同内容变更生成新版本，并只调整未来未使用期次。
5. 已开票、已回款和已核销数据不能被合同变更覆盖。
6. 项目重开继续使用原合同剩余额度，不重置合同总额或封顶额度。

### 10.4 财务联动

1. 项目暂停或终止后，按现有规则处理历史回款；已归档项目财务全部只读。
2. 项目归档前所有有效期次已经核销，重开不得恢复、修改或复制原期次。
3. 新应收明确关联合同版本和来源重开申请编号。
4. 历史发票保留原购方和合同版本。
5. 重开后新增回款记录真实付款方，不影响归档前历史回款。
6. 所有取消、作废、终止和冲正均保留原记录及审计轨迹。

## 11. 需要产品、业务和研发共同确认的决策项

1. 后端是否真实存在合同草稿记录；目标产品不展示独立草稿状态。
2. 已批准日报更正后，是否重新打开整份日报审批，还是只审批单条更正申请。本方案建议单条更正申请。
3. 项目重开后，在待合同状态下是否允许登记非计费工时。本方案建议允许受限的非计费准备工作。
4. 项目所属部门变化时是否需要原、新部门负责人双向审批。本方案建议需要。
