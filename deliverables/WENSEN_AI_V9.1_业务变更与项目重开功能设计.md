# 文森律所运营工作台 V9.1 业务变更与项目重开功能设计

## 1. 文档说明

### 1.1 设计目标

本方案基于 V9.1 当前产品能力，统一整理以下增量需求：

1. 工时代填、本人确认、退回及后续更正。
2. 审批中合同的撤回删除、重新上传和补充材料。
3. 已审批合同的文件更正、合同变更、作废及终止。
4. 已归档项目重新打开、误终止撤销和真实终止后的重新合作。
5. 项目重开时客户主体、负责人、成员和所属部门的调整。
6. 客户更名、增加客户主体、替换主客户及合同承继。
7. 项目、合同、应收、开票、回款和核销之间的联动。
8. 工时、合同、项目变更共用的审批、版本、权限和审计能力。

本方案只梳理产品功能与底层业务逻辑，不涉及代码实现。

### 1.2 V9.1 现状基线

以下能力已在 V9.1 或后续小版本中具备，本方案将其作为基础能力，不重复列为新开发范围：

- 统一工时台账。
- 本人登记工时。
- 受控代为填报工时。
- 承办律师确认或退回代填工时。
- “记录我的相关工时”。
- 管理统计、客户工时表、待确认与异常三个工时报表页签。
- 工时筛选、汇总和导出。
- 合同上传后形成合同记录并进入审批；当前不存在独立合同草稿状态。
- 项目、合同、结算期次、开票、回款和核销的基础关联。

本次需要补齐的是上述能力之间的状态衔接、变更机制和财务联动。

### 1.3 统一设计原则

1. **历史事实不可覆盖**：已经审批、生效、开票、回款或核销的数据不能被普通编辑覆盖。
2. **新增周期而非改写历史**：项目重开生成新的服务周期，原服务周期保持不变。
3. **确认与审批分离**：本人确认代表工时归属人认可，管理审批代表业务流程通过。
4. **先审批后生效**：合同变更、项目重开和已审批工时更正，在审批通过前均不影响正式数据。
5. **删除默认逻辑删除**：已经进入审批或产生下游数据的记录只能撤回、作废、终止或冲正。
6. **财务事实独立保留**：项目或合同状态变化不得自动删除应收、发票、回款和核销。
7. **主体身份与名称分离**：客户名称可以变化，但法律主体身份由稳定的客户 ID 和注册识别号确定。
8. **当前状态与历史快照并存**：页面展示当前有效数据，同时保留业务发生时的主体、负责人、合同和财务快照。

## 2. 总体业务对象与关系

### 2.1 核心对象

| 对象 | 作用 | 关键规则 |
| --- | --- | --- |
| 客户主数据 | 记录法律主体身份、名称历史和准入资料 | 客户 ID 稳定，名称可版本化 |
| 项目客户关系 | 记录某一服务周期内，各主体以何种角色参与项目 | 支持主客户、共同委托人、付款主体等 |
| 项目 | 记录服务执行过程 | 重开生成新服务周期，不改写原周期 |
| 合同 | 记录收费及法律依据 | 审批中可撤回重传，已审批后只能更正、变更、作废或终止 |
| 合同版本 | 记录合同正文及商业条款变化 | 同一时间只有一个当前有效版本 |
| 工时 | 记录个人实际工作和计费工时 | 归属人、提报人、确认状态和审批状态分离 |
| 应收期次 | 承接合同结算计划 | 不因项目重开而复制或重置 |
| 发票 | 记录真实开票事实 | 已开票后不能通过上游变更改写购方和金额 |
| 回款 | 记录真实到账事实 | 付款方可以不同于当前主客户 |
| 核销 | 记录回款与发票、应收之间的分配 | 已核销关系只能通过冲正调整 |
| 业务变更申请 | 承载合同变更、项目重开、工时更正等流程 | 统一记录原值、新值、原因、审批和生效时间 |

### 2.2 主链路

```text
客户主数据
  → 项目客户关系
  → 项目及服务周期
  → 合同及合同版本
  → 应收期次
  → 开票
  → 回款
  → 核销

项目及服务周期
  → 工时登记
  → 本人确认
  → 工时审批
  → 正式统计及客户工时表
```

### 2.3 变更链路

```text
原业务记录
  → 发起变更申请
  → 保存原始快照
  → 填写变更内容和原因
  → 展示影响范围
  → 审批
  → 审批通过后生成新版本或新周期
  → 原记录标记为历史、已更正、已作废或已终止
```

## 3. 工时管理模块

## 3.1 V9.1 已有能力

- 本人登记工时。
- 项目负责人、团队负责人、办公室工时管理员和系统管理员按授权范围代填工时。
- 分别记录承办律师与提报人。
- 代填原因必填。
- 代填后进入“待本人确认”。
- 承办律师可确认或退回。
- 待确认工时不进入正式统计和客户工时表。
- 支持从他人记录复用公共工作信息，创建本人独立工时。
- 工时报表和异常页签已完成小版本迭代。

## 3.2 需要新增的功能

### 3.2.1 工时状态拆分

工时需要同时记录三个维度的状态，避免用一个字段混合表达不同含义。

| 状态维度 | 状态值 |
| --- | --- |
| 登记来源 | 本人登记、代为填报、相关工时复用、历史导入 |
| 本人确认 | 不适用、待本人确认、已确认、已退回 |
| 管理审批 | 未提交、审批中、已通过、已退回、已撤回 |
| 记录有效性 | 当前有效、更正审批中、已被更正、作废审批中、已作废、已锁定 |

### 3.2.2 代填撤回和再次提交

- 待本人确认时，代填人可以撤回。
- 撤回后可以修改工作内容、时长、项目和附件。
- 再次提交后重新通知承办律师。
- 承办律师退回时必须填写退回原因。
- 已确认的代填记录不能由代填人直接修改。

### 3.2.3 审批中工时撤回

- 审批尚未完成时，登记人可以撤回。
- 撤回后原审批任务关闭。
- 修改后重新提交，生成新的审批申请编号。
- 已处理审批节点保留为历史，不恢复原审批任务。

### 3.2.4 已审批工时更正

新增“申请更正”，支持修改：

- 工作日期。
- 客户及项目。
- 工作类型和工作方式。
- 工作内容。
- 实际工时和计费工时。
- 完成状态。
- 备注和附件。

更正流程：

```text
已审批工时
  → 申请更正
  → 填写新值和原因
  → 展示修改前后差异
  → 原审批人或项目负责人审批
  → 通过后生成新版本
  → 原版本标记为“已被更正”
```

审批期间继续使用原工时参与正式统计；新版本只有审批通过后才进入报表。

### 3.2.5 已审批工时作废

- 已审批记录不得直接删除。
- 增加“申请作废”。
- 作废原因必填。
- 审批通过后退出正式统计、客户工时表和绩效统计。
- 原记录保留并显示“已作废”。

### 3.2.6 承办律师变更

承办律师变更不属于普通工时更正，单独处理：

- 仅项目负责人、工时管理员或系统管理员可发起。
- 记录原承办律师、新承办律师和转移原因。
- 通知双方。
- 审批通过后变更工时归属。
- 原提报人及原登记来源保持不变。

### 3.2.7 工时锁定期间

满足以下任一条件时标记为已锁定：

- 已纳入关闭的月度绩效期间。
- 已向客户出具正式工时报表。
- 已作为计费或开票依据。
- 已进入薪酬或业绩结算。

锁定记录只能发起特殊更正，由项目负责人和相应管理人员审批；不能普通编辑或普通作废。

## 3.3 底层逻辑

1. 工时每次更正生成新版本，不覆盖原记录。
2. 正式报表只读取当前有效、已确认、已审批、未作废的版本。
3. 代填确认完成后，才进入现有正常审批或正式统计流程。
4. 更正审批期间继续使用原有效版本。
5. 工时作废只改变有效性，不物理删除数据。
6. “记录我的相关工时”只复用客户、项目、日期、工作类型和内容摘要，不复用时长、承办律师和私人附件。
7. 已归档或已终止项目不允许新增工时，但允许处理归档或终止前的待确认、退回和更正事项。

## 4. 客户主数据与项目客户主体模块

## 4.1 需要新增的客户主体能力

### 4.1.1 同一法律主体名称变更

适用于注册识别号不变、仅主体名称变化的情况。

新增功能：

- “主体名称变更”入口。
- 原名称、新名称和生效日期。
- 注册号或统一社会信用代码。
- 名称变更证明上传。
- 曾用名列表。
- 使用历史名称搜索客户。

底层逻辑：

- 客户 ID 不变。
- 客户当前名称更新。
- 历史项目、合同、应收、发票和回款保留业务发生时的名称快照。
- 不因更名新建重复客户。

### 4.1.2 项目增加客户主体

项目由单一客户字段升级为“一个主客户＋多个项目参与主体”。

支持的主体角色：

| 角色 | 业务含义 |
| --- | --- |
| 主客户 | 项目默认归属和默认报表客户 |
| 共同委托人 | 与主客户共同委托 |
| 服务对象 | 实际接受法律服务 |
| 付款主体 | 承担全部或部分付款义务 |
| 发票抬头主体 | 接收发票 |
| 指令来源主体 | 发出业务指令 |
| 受益主体 | 项目结果主要受益方 |
| 关联方 | 与项目相关但不是委托人 |
| 对方当事人 | 利冲对象，不属于客户 |

新增项目主体时记录：

- 主体。
- 主体角色。
- 与主客户的关系。
- 生效日期和结束日期。
- 联系人。
- 是否进入合同。
- 是否承担付款责任。
- 是否作为发票抬头。
- 文件访问权限。

### 4.1.3 替换项目主客户

适用于合并、分立、合同转让、债务承继或委托主体替换。

新增“项目客户主体变更”申请，记录：

- 原主客户和新主客户。
- 变更原因及法律关系类型。
- 生效日期。
- 是否承继合同。
- 是否承继未开票应收。
- 是否承继已开票欠款。
- 是否承继预付款。
- 证明文件。

主体替换生效前必须完成客户准入、利冲、AML 或必要的合规核验。

## 4.2 项目重开中的客户主体操作

项目重开页面增加“本次是否变更客户关系”：

- 不变。
- 同一主体名称变更。
- 增加客户主体。
- 替换主客户。
- 移除共同客户。
- 调整主体角色。

系统根据选择提示：

- 是否需要重新利冲。
- 是否需要合同变更。
- 是否影响未开票应收。
- 是否影响开票抬头。
- 是否存在原主体欠款。
- 是否需要重新配置文件权限。

## 4.3 底层逻辑

1. 客户主数据记录法律主体身份和名称历史。
2. 项目客户关系记录某个服务周期内主体参与项目的角色。
3. 合同保存签署时的主体快照，不跟随客户名称自动改写合同正文。
4. 财务对象保存发生时的债务主体、发票购方和实际付款方快照。
5. 同一法律主体更名不转移应收；不同法律主体承继必须走主体变更及财务审批。
6. 对方当事人与客户主体使用不同关系类型，不能混入客户统计。

## 5. 项目生命周期与项目重开模块

## 5.1 项目状态定义

| 状态 | 含义 | 是否允许新增业务 |
| --- | --- | --- |
| 项目审批中 | 立项尚未完成 | 否 |
| 待合同/待补充协议 | 项目可准备，但收费依据未完成 | 限制性允许 |
| 进行中 | 正常履约 | 是 |
| 暂停 | 临时停止履约 | 否，但可处理历史财务 |
| 待结项 | 正在完成结项检查 | 原则上否 |
| 已归档 | 正常完成并进入只读 | 否 |
| 已终止 | 未正常完成而提前结束 | 否 |
| 重开申请中 | 正在审批是否恢复业务 | 否 |

### 5.1.1 已归档

表示项目正常完成，成果、工时和审批已经处理，项目进入只读状态。后续出现补充工作时可以申请重新打开。

### 5.1.2 已终止

表示项目因客户撤回、合同解除、利益冲突、长期欠款或外部原因提前结束。真实终止后重新合作原则上新建项目；误操作终止可以申请撤销。

## 5.2 项目重新打开

已归档项目增加“申请重新打开”。

申请内容包括：

- 重开类型：补充服务、继续履行、误归档恢复。
- 重开原因。
- 新服务范围。
- 重开日期和新预计结束日期。
- 当前项目负责人。
- 当前项目成员。
- 项目所属部门或团队。
- 是否继续使用原合同。
- 是否需要补充协议或新合同。
- 当前风险说明。
- 是否重新利冲。
- 新周期预算工时和业务归属。

审批通过后生成新的服务周期，项目编号不变。

## 5.3 误终止撤销与真实终止后重新合作

### 5.3.1 误操作终止

- 增加“撤销终止”。
- 填写误操作原因。
- 由原终止审批人审批。
- 通过后恢复到终止前状态。
- 保留终止和撤销终止记录。

### 5.3.2 真实终止后重新合作

- 原项目保持已终止。
- 新建项目并关联原项目。
- 复用客户和基础资料。
- 重新完成准入、利冲、立项和合同流程。

## 5.4 项目重开时的字段编辑控制

### 5.4.1 允许编辑的新周期字段

- 重开原因和类型。
- 新服务范围。
- 新服务周期起止日期。
- 当前项目负责人。
- 当前项目成员。
- 项目所属部门或团队。
- 当前服务阶段。
- 合同使用方案。
- 风险说明。
- 新周期预算工时和分配方案。

### 5.4.2 有条件修改的字段

| 字段 | 规则 |
| --- | --- |
| 项目名称 | 仅允许合理更正或补充，不改写历史显示名称 |
| 项目所属部门 | 原、新部门负责人共同确认，历史归属不重算 |
| 主客户 | 必须走客户主体变更、重新利冲和合同处理 |
| 项目服务类型 | 本质变化时应新建项目，不能通过重开修改 |
| 我方签约主体 | 通过合同变更或新合同处理，不能直接改项目历史 |

### 5.4.3 不允许修改的历史事实

- 项目编号。
- 原创建时间。
- 原立项审批。
- 原服务周期。
- 原归档或终止时间和原因。
- 原项目负责人及历史成员快照。
- 原合同及合同版本。
- 历史工时。
- 历史应收、发票、回款和核销。
- 原周期业绩分配。

## 5.5 项目组织角色

项目中区分：

- 项目负责人：负责项目执行。
- 项目成员：参与具体工作。
- 项目所属部门或团队：项目当前组织归属。
- 所属部门负责人：从 HR 组织架构自动带出，负责管理审批。

所属部门负责人不在项目中手工指定。变更项目所属部门时，由系统取得原部门负责人和新部门负责人，并按规则生成审批节点。

## 5.6 底层逻辑

1. 项目重开生成新的服务周期，不覆盖原项目周期。
2. 项目当前负责人、成员和部门可以变化，但历史周期保留历史快照。
3. 原合同、工时和财务数据继续关联原服务周期。
4. 新周期产生的新合同、工时和财务数据关联新服务周期。
5. 项目重开本身不自动增加合同额、应收或工时额度。
6. 重开审批中项目继续只读。
7. 重开通过后，根据合同情况进入“进行中”“待合同”“待补充协议”或“待利冲”。

## 6. 合同管理模块

## 6.1 合同状态

V9.1 不增加草稿状态，合同上传后进入以下状态：

```text
审批中
  ├─ 撤回并删除 → 已删除（仅审计可见）
  ├─ 重新上传 → 新审批流程
  ├─ 审批拒绝 → 已拒绝
  └─ 审批通过 → 已审批

已审批
  ├─ 文件更正 → 更正审批
  ├─ 合同变更 → 新合同版本
  ├─ 作废登记 → 已作废
  └─ 提前结束 → 已终止
```

## 6.2 审批中合同新增功能

### 6.2.1 撤回并删除

- 仅上传人或项目负责人可操作。
- 关闭当前审批任务并标记“申请人撤回”。
- 合同退出普通台账。
- 合同编号、文件和操作日志在审计中保留。

### 6.2.2 重新上传合同

- 合同编号保持不变。
- 原文件标记为已替换。
- 原审批流程终止。
- 上传新文件并填写重传原因。
- 生成新的审批申请编号。
- 审批人可以查看新旧文件。

### 6.2.3 补充材料

- 适用于增加附件但不替换合同正文。
- 不重新启动审批。
- 审批详情通知材料已补充。
- 记录补充人和时间。

## 6.3 已审批合同新增功能

### 6.3.1 合同文件更正

适用于错传、漏页或扫描不清，但合同内容未发生变化。

- 上传正确文件。
- 填写更正原因。
- 原审批人确认。
- 新文件成为当前展示版本。
- 原文件保留为历史版本。
- 不调整合同金额和财务数据。

### 6.3.2 合同变更

适用于主体、范围、期限、金额、税率、付款方式、收款账户、结算计划或团队分配变化。

- 创建合同新版本。
- 记录原值、新值和差异。
- 上传补充协议或变更依据。
- 审批期间原合同版本继续有效。
- 审批通过后新版本生效。

### 6.3.3 作废合同登记

- 无结算、开票、回款和核销数据时可以申请作废。
- 有未使用结算期次时，审批通过后同步取消。
- 已产生开票、回款或核销时不允许作废，只能终止或走财务冲正。
- 作废后保留合同编号、原文件和审批记录。

### 6.3.4 合同终止

- 填写终止原因和生效日期。
- 说明未履行工作。
- 处理未来结算期次。
- 保留已发生应收、开票、回款和核销。
- 提示是否同步暂停或终止项目，但不自动改变项目状态。

## 6.4 合同与项目重开联动

| 合同情况 | 重开后的项目状态 | 处理 |
| --- | --- | --- |
| 已审批、未到期、范围覆盖 | 进行中 | 继续使用原合同，不复制期次 |
| 已审批、未到期、范围不覆盖 | 待补充协议 | 补充协议批准后开放收费业务 |
| 已到期 | 待合同 | 续签、补充协议或新合同 |
| 已终止 | 待合同 | 原合同不能重新激活 |
| 已作废 | 待合同 | 不得作为重开依据 |
| 合同审批中 | 待合同审批 | 不生成新应收和开票 |
| 合同变更审批中 | 待合同变更 | 原版本继续处理原业务 |

## 6.5 合同金额和结算计划逻辑

1. 未开票、未回款的未来期次可以通过合同变更调整或取消。
2. 开票审批中的期次必须先处理审批，不能直接修改。
3. 已开票、已回款、已核销的期次不可覆盖。
4. 调减后的合同金额不得低于已开票金额或已确认收入。
5. 调增时只生成增量结算期次，不复制原期次。
6. 无封顶小时合同按实际确认或开票金额累计，不预设固定合同总额。
7. 有封顶小时合同重开后继续使用剩余额度，不重置封顶额度。
8. 基础费用与预计风险费用分开记录；风险费用满足触发条件后再形成正式应收。

## 7. 财务应收模块

## 7.1 需要新增的功能

### 7.1.1 服务周期字段

应收期次增加“所属服务周期”，区分原项目周期和重开周期。

### 7.1.2 应收来源和版本

记录应收来源：

- 原合同结算计划。
- 合同变更调增。
- 补充协议。
- 新合同。
- 授权的无合同手工应收。
- 主体变更转入。

### 7.1.3 主体变更转出和转入

未开票应收经合同承继和财务审批后可以转移：

1. 原应收标记“主体变更转出”。
2. 保留原债务主体、原金额和原编号。
3. 针对未开票余额生成新主体应收。
4. 新应收关联原应收编号。
5. 转出和转入金额必须一致。

## 7.2 项目重开对应收的规则

项目重开本身不生成应收，也不复制或重置原应收。

| 原应收状态 | 重开后的处理 |
| --- | --- |
| 未到期、未开票 | 保持原状态 |
| 已到期、未开票 | 继续显示逾期 |
| 开票审批中 | 继续原审批 |
| 已开票 | 保持已开票 |
| 部分回款 | 保持已回款和剩余金额 |
| 已回款 | 保持已回款 |
| 已核销 | 完全锁定 |
| 已取消 | 不自动恢复 |
| 因终止而暂停 | 在重开或合同变更审批中明确是否恢复 |

## 7.3 新增应收的前置条件

- 项目重开已通过。
- 合同、补充协议或新合同已审批通过。
- 结算条件和金额明确。
- 不与原期次重复。
- 币种、税率和收款主体一致。
- 明确关联新服务周期。

## 7.4 底层逻辑

1. 应收是独立财务对象，不随项目状态直接删除。
2. 应收保存生成时的客户、合同和结算条款快照。
3. 逾期日期不因项目重开而重置。
4. 取消和转移均保留原记录，通过状态和关联记录表达变化。
5. 项目应收金额按全部当前有效期次扣除取消和批准调减金额计算。

## 8. 开票模块

## 8.1 需要新增的功能

- 开票选择链路增加服务周期：项目 → 服务周期 → 合同 → 应收期次。
- 开票列表展示客户主体、合同版本和服务周期。
- 客户更名后，开票申请默认读取当前有效开票资料，并提示签约时名称。
- 多客户项目中明确选择发票抬头主体。
- 主体替换时提示原主体未结应收和历史发票。

## 8.2 底层逻辑

1. 历史发票保留实际购方名称、税号、金额和开票日期，不随客户名称变化自动修改。
2. 项目重开不复制或重新生成历史发票。
3. 新开票只能选择当前有效、未取消且有可开票余额的应收。
4. 待合同、待补充协议和合同审批中的项目不得新增正式开票申请。
5. 已开票应收需要更换购方时，必须先完成发票红冲或作废，再生成新发票；不能直接修改购方。

## 9. 回款与核销模块

## 9.1 需要新增的功能

- 回款页面展示项目、服务周期、合同、发票和应收期次。
- 支持实际付款方不同于当前主客户。
- 第三方代付时记录代付关系并上传说明。
- 历史回款登记错误通过回款冲正处理。
- 项目重开后可以分别查看原周期和新周期的回款。

## 9.2 项目状态与回款权限

以下项目状态仍允许针对历史发票登记回款和核销：

- 暂停。
- 已归档。
- 已终止。
- 重开申请中。
- 待合同或待补充协议。

项目是否继续履行不能阻断历史债权的收款。

## 9.3 底层逻辑

1. 回款记录真实到账币种、金额、付款方和日期。
2. 核销记录回款与具体发票、应收期次之间的分配。
3. 项目或客户主体变化不自动修改历史核销关系。
4. 原合同回款不得通过项目重开转移到新合同。
5. 错误回款通过整笔冲正或受控调整处理，不直接覆盖。

## 10.1 统一变更申请类型

- 合同重新上传。
- 合同文件更正。
- 合同内容变更。
- 合同作废。
- 合同终止。
- 项目重新打开。
- 撤销误终止。
- 项目客户主体变更。
- 项目所属部门变更。
- 工时更正。

- 承办律师变更。
- 锁定工时特殊更正。

## 10.2 统一申请状态

- 待提交。
- 待本人确认。
- 审批中。
- 已通过。
- 已退回。
- 已撤回。
- 已作废。
- 已生效。

“待本人确认”仅表达业务归属人确认，不等同于管理审批。

## 10.3 统一审批详情

审批详情必须展示：

- 业务对象和原记录编号。

- 申请原因。
- 原值和新值对比。
- 相关附件。
- 生效日期。

- 审批节点和历史操作。

## 10.4 待办入口

个人工作台新增或整合以下待办：

- 代填工时待确认。
- 退回工时待修改。
- 工时更正或作废审批。
- 合同重传、文件更正、变更、作废或终止审批。
- 项目重开或撤销终止审批。
- 客户主体及项目所属部门变更审批。
- 合同、利冲或财务条件待补充。

## 11. 权限模块

## 11.1 工时权限

| 角色 | 权限 |
| --- | --- |
| 普通成员 | 登记本人、撤回本人审批中记录、申请本人已审批工时更正 |
| 项目负责人 | 为负责项目成员代填、审核项目工时更正、发起承办律师变更 |
| 团队负责人 | 为本团队成员代填及审核异常工时 |
| 办公室工时管理员 | 处理本办公室代填和锁定期特殊更正 |
| 系统管理员 | 授权范围内特殊处理，但仍保留审计记录 |

## 11.2 项目重开权限

可发起人：

- 原项目负责人。
- 项目所属部门负责人。
- 办公室业务管理员。
- 系统管理员。

普通项目成员可以提交重开建议，但不能直接发起正式重开审批。

## 11.3 合同变更权限

- 合同上传人或项目负责人可以撤回审批中合同。
- 已审批合同的文件更正和内容变更由项目负责人或合同负责人发起。
- 合同作废和终止需要原合同审批人及必要的财务审批。
- 已产生财务数据后，系统管理员也不能绕过审批直接删除合同。

## 11.4 客户主体变更权限

- 项目负责人发起。
- 客户主数据管理员核验主体身份。
- 利冲负责人完成冲突检查。
- 涉及合同的由合同审批人审核。
- 涉及应收转移、发票抬头或付款主体的由财务审核。

## 12. 公共底层能力

## 12.1 版本管理

需要为以下对象提供版本：

- 客户名称。
- 项目客户关系。
- 项目服务周期。
- 项目负责人、成员和所属部门快照。
- 合同正文和合同条款。
- 工时记录。

每个版本记录：

- 版本号。
- 原记录 ID。
- 当前有效标识。
- 生效日期和失效日期。
- 创建人和创建时间。
- 变更来源申请。

## 12.2 业务快照

合同、应收、发票、回款等业务对象保存业务发生时的关键快照：

- 客户名称和主体识别号。
- 项目名称和服务周期。
- 合同编号和合同版本。
- 签约主体和服务团队。
- 币种、税率和金额。
- 发票购方和实际付款方。

客户主数据后续变化时，历史快照不被覆盖。

## 12.3 影响分析

提交变更前，系统计算并展示：

- 是否影响合同金额。
- 是否影响结算期次。
- 是否存在审批中开票。
- 是否存在已开票、已回款或已核销数据。
- 是否影响项目状态。
- 是否影响正式工时和客户报表。
- 是否需要重新利冲。
- 是否需要新合同或补充协议。

## 12.4 审计日志

统一记录：

- 谁在什么时间发起了什么操作。
- 修改前和修改后内容。
- 撤回、退回、拒绝、通过和生效记录。
- 文件替换和版本变化。
- 自动校验结果。
- 财务联动结果。

审计日志不能由普通用户删除。

## 12.5 逻辑删除与冲正

| 业务对象 | 错误处理方式 |
| --- | --- |
| 审批中合同 | 撤回并逻辑删除 |
| 已审批合同 | 文件更正、变更、作废或终止 |
| 已审批工时 | 更正或作废 |
| 应收期次 | 取消、调减、主体转出 |
| 发票 | 作废或红冲 |
| 回款 | 整笔冲正或受控调整 |
| 核销 | 随回款冲正撤销或重新分配 |

## 13. 跨模块联动规则

## 13.1 项目归档前检查

必须检查：

- 是否存在审批中合同。
- 是否存在待确认代填工时。
- 是否存在审批中或退回未处理的工时。
- 是否存在未完成合同变更。
- 是否存在未处理项目审批。
- 是否存在未完成应收、开票、回款和核销事项。

财务未完全结束时可以根据管理规则归档，但系统必须显示未结财务事项，并继续允许收款和核销。

## 13.2 项目终止前检查

除归档检查外，还需要确认：

- 是否同步终止合同。
- 未完成服务如何处理。
- 未结算工时如何处理。
- 剩余应收是否继续追收。
- 待确认代填工时由谁处理。
- 项目文件是否完成交接。

## 13.3 项目重开影响摘要

提交重开申请前展示：

| 影响项 | 内容 |
| --- | --- |
| 项目 | 原状态、目标状态、新服务周期 |
| 客户 | 主客户及新增、替换主体 |
| 组织 | 原负责人、新负责人、原部门、新部门 |
| 成员 | 保留、新增、移除人员 |
| 合同 | 有效、到期、终止、待变更及剩余额度 |
| 应收 | 未开票、逾期、已开票金额 |
| 回款 | 已回款、未回款、待核销 |
| 工时 | 历史工时、待确认和异常工时 |
| 风险 | 利冲、欠款、合同及交付风险 |
| 重开限制 | 待合同、待补充协议、待利冲等 |

## 13.4 项目状态与业务权限矩阵

| 项目状态 | 新增工时 | 合同操作 | 新增应收/开票 | 历史回款/核销 |
| --- | --- | --- | --- | --- |
| 进行中 | 允许 | 允许 | 允许 | 允许 |
| 待合同 | 仅非计费或受限工时 | 允许上传合同 | 不允许 | 允许 |
| 待补充协议 | 准备工作受限 | 允许合同变更 | 不允许新增收费业务 | 允许 |
| 暂停 | 不允许新增 | 只读或受控变更 | 不允许新增 | 允许 |
| 已归档 | 不允许新增 | 文件更正等受控操作 | 不允许新增 | 允许 |
| 已终止 | 不允许新增 | 终止后只读 | 不允许新增 | 允许 |
| 重开申请中 | 不允许新增 | 只读 | 不允许新增 | 允许 |

## 13.5 数据汇总口径

1. 项目重开本身不增加合同额。
2. 合同额按当前有效合同版本及批准的变更差额计算，不能重复累计多个版本。
3. 应收按当前有效期次汇总，扣除已取消和批准调减金额。
4. 已开票按真实发票汇总。
5. 已回款按真实到账记录汇总。
6. 核销按回款与发票的真实分配汇总。
7. 原服务周期和重开服务周期分别统计，同时支持项目整体汇总。
8. 项目归档时保存经营快照；重开后展示当前口径，但不回写原归档快照。

## 15. 建议实施分期

### 15.1 第一期：核心闭环

- 代填撤回、退回修改和再次确认。
- 已审批工时更正及作废。
- 审批中合同撤回删除、重新上传和补充材料。
- 已审批合同文件更正。
- 已归档项目重新打开。
- 服务周期模型。
- 统一变更记录、版本和新旧值对比。

### 15.2 第二期：合同与财务联动

- 合同内容变更。
- 合同金额和结算期次调整。
- 合同作废及终止。
- 新服务周期与应收、开票、回款联动。
- 客户主体变更及未开票应收承继。
- 项目归档和终止完整性检查。

### 15.3 第三期：复杂治理

- 锁定期间工时特殊更正。
- 发票红冲或作废闭环。
- 跨办公室项目部门变更。
- 多客户复杂付款责任。
- 统一业务变更与异常管理中心。
- 经营快照及历史口径对比。

## 16. 核心验收标准

1. 审批中合同可以撤回删除或重新上传，且原审批记录可追溯。
2. 已审批合同不能被直接覆盖或物理删除。
3. 已归档项目重开后形成新服务周期，原周期数据保持不变。
4. 已终止项目不能以普通重开方式恢复；误终止撤销与真实重新合作规则明确。
5. 项目负责人、成员和所属部门可以在新周期调整，历史组织归属不重算。
6. 同一客户更名不产生重复客户，历史合同和财务快照不被改写。
7. 新增或替换客户主体必须完成利冲及必要的合同、财务审批。
8. 项目重开不自动生成或复制应收、发票和回款。
9. 已开票、已回款和已核销数据不能被合同或项目变更覆盖。
10. 已审批工时只能通过更正或作废流程调整。
11. 待确认代填工时不进入正式统计；更正审批期间继续使用原有效版本。
12. 暂停、归档、终止或重开审批中的项目仍可处理历史回款和核销。
13. 所有变更均能查询申请原因、原值、新值、审批记录、生效时间和操作人。
